# Prompt Library

## Context Management

Prompts for preserving or transferring conversation state.

### Compact — preserve decisions & changes

`/compact` — Preserve all decisions, changes, and additions made this session. Prioritize: (1) explicit decisions/confirmations, (2) file changes and additions, (3) rationale behind them. Compress general discussion/exploration first.

### Handoff summary — resume in new chat

Act as an expert technical archivist. Generate a comprehensive handoff summary of our entire conversation so far. Format it so I can paste it directly into a brand-new chat to resume work seamlessly without losing context. Include: (1) Core project goals and overall objective, (2) Key decisions made and constraints established, (3) Current technical stack, file structures, or core components discussed, (4) Exact state of what we just finished, and (5) The immediate next steps or open tasks we need to tackle. Be dense with technical specifics, code snippets or logic paths if applicable, but concise enough to fit efficiently into a new context window.

## UI/UX Animation & Transitions

Prompts for auditing and upgrading motion design in a frontend codebase.

### Motion audit & upgrade — principles + reusable patterns

Act as a senior motion/interaction designer doing a paid audit of this codebase's animations and transitions, then fixing what you find. Start with inventory and restraint, not output: list every place motion currently exists (CSS transitions/keyframes, animation libraries like Framer Motion, custom hooks that gate animation lifecycle, autoplay/carousel logic) and every place it's conspicuously absent on interactive elements (buttons, cards, modals, menus, toggles, form validation, loading/empty states) — but don't propose motion just because a gap exists; only add it where it does a job: acknowledging an action, making a state change or spatial relationship legible, preserving continuity through navigation/layout change, directing attention at a meaningful moment, or embodying the product's identity in one authored focal moment. Scattered, unmotivated animation is exactly what makes an interface read as AI-generated — one deliberate, orchestrated moment beats several small competing ones, and for anything you're about to add, write a one-line thesis first (the focal moment, if any; what continuity or feedback it serves; the performance budget) before implementing it.

Score everything that exists (and everything you're about to add) against this checklist, citing file:line for every violation:
- **Timing & easing** (Disney's 12 principles, adapted for web, refined by purpose): 100-150ms for immediate feedback, 150-300ms for a routine state change, 300-500ms for a layout/overlay/view transition, 500-800ms only for a deliberately authored focal entrance — longer than that reads as latency, not intent. Entrances use ease-out (natural deceleration, e.g. `cubic-bezier(0.16, 1, 0.3, 1)`), exits are faster than entrances and use ease-in; similar elements share identical timing values; springs (not eased tweens) for any overshoot-and-settle motion; no bounce/elastic curves by reflex; stagger delays ≤50ms/item, capped total, and never turn every scrolled section into a staggered list just because one exists; only one focal point animates prominently at a time; modal/dialog backgrounds dim to direct focus.
- **Hard constraints** (non-negotiable, flag any violation as a bug not a style note): animate compositor-friendly properties — `transform`, `opacity` — by default; never `width`, `height`, `top`, `left`, `margin`, `padding` (use FLIP/transform techniques instead); treat `background`/`color`/`filter`/`blur`/shader work as the exception, not the default — reserve it for a bounded, isolated region where the material itself is the point (a focal moment), never applied broadly for decoration. Never `transition: all`. `will-change` only ever on `transform`/`opacity`/`filter`, and only while an animation is actually active, never left on at rest. Looping/ambient animation pauses when scrolled off-screen. `prefers-reduced-motion` gets an intentional reduced alternative (state still changes, it just doesn't animate) rather than a blanket kill.
- **Interface-polish details**: interruptible CSS-transition state changes for anything interactive (reserve one-shot keyframes for staged sequences that run once); split enter animations into staggered chunks rather than animating one container; exits subtler than enters (small fixed offset, not a full reverse of the entrance); icon-only buttons get `aria-label`; scale-on-press at exactly `0.96` (never below `0.95` — it starts to feel exaggerated); contextual icon cross-fades instead of hard visibility toggles; `AnimatePresence` (or equivalent) uses `initial={false}` so nothing plays an unwanted entrance on first page load.
- **Visual QA pass**: separately from the checklist above, look for motion that's simply janky or inconsistent in practice — animations that feel slow, stutter, fight with each other, or make near-identical interactions (two similar buttons, two similar cards) behave with different timing or easing for no reason. For every animation kept or added, apply the gut check: would removing it lose meaning or authored character, or was it decoration?

Then, for gaps where a well-tested, accessible pattern already exists rather than a bespoke one — dropdowns, modals, panel reveals, notification badges, success confirmations, input-shake on validation error, page transitions, icon swaps, number pop-ins — pull the matching transition from transitions.dev (https://transitions.dev, `npx transitions-pro`, or its agent skill) instead of hand-rolling it; its `t-*` snippets already ship with `@media (prefers-reduced-motion: reduce)` guards and semantic custom properties, so adapt them to this project's existing motion tokens/hooks rather than importing a second animation system. Respect whatever animation lifecycle/gating hooks and design tokens the project already has (e.g. an intro-motion hook that plays once, stops on interaction, and pauses off-screen) — extend that pattern to new motion instead of introducing a competing one. If the Impeccable skill (`/impeccable`) is available in this environment, hand off implementation of confirmed gaps to `/impeccable animate` (it holds the same focal-moment/restraint discipline and a runtime-appropriate technique menu) and close with `/impeccable polish` as the final pass. Deliver: (1) the audit table of violations grouped by checklist category, (2) a prioritized list of missing-motion opportunities with the exact transitions.dev pattern or hand-written values to use for each (and an explicit "skip" note for any gap that's better left unanimated), (3) the diffs applied, as before/after tables — nothing that changes behavior or copy outside of motion/timing/easing.
